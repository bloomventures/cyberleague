# Cyberleague

Cyberleague is a platform for devs to write bots to play games against other bots.

Components:

- API - main api supporting the web app and CLI
- Web App - displays bots and results
- Coordinator - job to run games
- CLI - create bots locally, build, test, deploy
- Evaluator - server that runs bots in sandboxed environments

## Games

Games are defined in Clojure:

  - in a data map, including:
     - name, slug, description, rules documentation
     - specs for moves, state
  - in a protocol, including various functions, including:
     - valid-move?, next-state, game-over?, winner

For more details, see ADDING_GAMES_GUIDE.md


## Bots

- all bots receive single input as JSON (or something similar) and must return a move as JSON
- the specs for input and output are different for each game

- devs may write their bots in any language that is supported
- all bots result in a single artifact file (a zip when necessary)


- language specifics:
  - clojure
    - input/output is EDN instead


## Envs

- every bot must specify an "env", which dictates how it is invoked on the server
- some languages may have multiple related envs (clojure: java-uberjar, babashka)

- see `./cl list envs" for an up-to-date list of languages and envs

- env specifics:
    - clojure
        - actually just a java environment, expects an uberjar
        - deps: java
        - expects: bot.jar


## Web API

HTTP API that powers the Web APP and CLI.

Currently, optimized for TADA CLJ RPC (ie. not a REST API).

endpoints (currently, just documenting those relevant to game running)

```
POST /bot/upload
    params:
      env: "clojure"
      bot-id: (uuid)
      artifact: (file)
    header:
      auth-token

  checks:
     limits on artifact size
     auth->user-id
       user exists
       bot exists
       user owns bot

  stores the artifact
    via EVALUATOR/upload
    and in db:
      artifact/id: uuid
      artifact/digest: sha256
      artifact/at: inst
      artifact/bot: ref->bot-id


  performs a basic test and reports errors
    via EVALUATOR/run


POST /bot/test
  params:
      bot-id: (uuid)
  header:
    auth-token

  checks:
    auth->user-id
      user exists
      bot exists
      user owns bot
    rate limit (to prevent CPU abuse)

  pull up the related bot (& game & dummy opponent)
  run game
      via EVALUATOR/run


POST /bot/release
   mark which one is live
    bot/live-artifact: ref->artifact-id
```

## Evaluator

- abstract code evaluator, doesn't know anything about games

- minimal environment generated by nix, for running just the supported languages

- libkrun used as the vm for sandboxing

- see `./cl list envs` for an up-to-date list of languages and envs

- http server with minimal interface:

```
POST /upload
    params
      env: "clojure"
      artifact: (file)
    header:
      admin-auth-token

    stores the artifact
    returns the digest

POST /run
  params:
    artifact-digest: (uuid)
    input: (json)
  header:
    admin-auth-token

  check:
    token

  runs bot with input passed in
  inside a libkrun + nix vm
  returns output
```


## VM

To run arbitrary code safely, we leverage Firecracker microVMs.

To reduce time-to-eval, we make use of "snapshotting". To evaluate a binary after a snapshot is made, we include a relay program in the VM, that receives binaries over vsock.


### VM Generation

Firecracker needs a root-fs ext4 image and a kernel image.

  - root-fs is generated by nix, from cyberleague.nix
  - kernel-image is pulled from the Firecracker CI

`build.sh` is used to prepare the necessary files for the VM:

```
/vm/
  ./firecracker - executable from the firecracker release
  ./jailer - executable from the firecracker release
  ./vmlinux - uncompressed linux kernel binary in ELF format, fetched from firecracker's CI (vm here stands for "virtual memory")
  ./initramfs.cpio.gz
    - root filesystem built by nix (containing python) and init.sh (which the vm is configured to run)
    - in the form of a ramdisk (rather than sqsh) because:
      - vm needs to be able to write to it
      - if sqsh, writing would modify the file (making it not reusable between vm runs or in parallel)
      - ramdisk gets loaded, is writable, but doesn't affect the original file
  ./sidecar.sqsh
    - squashfs filesystem image of an extra disk
    - mounted as readonly
    - contains JRE, the relay program
    - JRE here because it's big
    - relay here to make iteration faster (than rebuilding initramfs)
    - (generally, keeping initramfs small is faster and requires less RAM on the system)
```

 We use the above, while running the jailer, to create a snapshot.
 Using snapshots saves ~2s of boot time.
 We use the jailer during snapshot creation, so that the sock files that firecracker expects are always in the same place (from the jailed perspective)

 ```
 /vm/
  ./snapshot/
    ./firecracker.mem - snapshot of the RAM
    ./firecracker.snap - metadata re the VM config
```

Use use the jailer+fircker to load a snapshot.

The jailer creates a new chroot:

```
/vm/
  ./jailer_roots/
    ./firecracker/
      ./{UUID}/
        ./root/
          ./firecracker.socket - socket file created by firecracker process (to communicate with the firecracker process)

          ./firecracker - hardlink to the firecracker executable (/vm/firecracker)
          ./vmlinux - hardlink to the kernel image (/vm/vmlinux)
          ./initrd.gz - hardlink to the init fs image (/vm/initramfs.cpio.gz)
          ./sidecar.img - hardlink to the sidecar disk image  (/vm/sidecar.sqsh)

          when run from snapshot, also:
          ./firecracker.snap - hardlink to /vm/snapshot/firecracker.snap
          ./firecracker.mem - hardlink to /vm/snapshot/firecracker.mem

          ./v.sock - vsocket file created by firecracker when relay starts listening on port 5525, use by evaluator process to communicate with relay process (guest<->host) (security-sensitive, potential attack vector)
```

### Relay

The relay is a program that runs inside of the firecracker VM, which executes binaries based on instructions from the host.

- host sends CBOR-encoded message over socket
- a message contains:
  - artifact (binary)
  - stdin (binary)
  - argv (array of strings, command to eval in guest, $ARTIFACT available)
- guest listens over vsock
- guest executes
- guest returns a CBOR-encoded message, containing:
  - exit (integer)
  - stdout (string)
  - stderr (string)

Might be safer to use a stricter binary encoding than CBOR.
